# Replace the MoE work decomposition

> Historical research snapshot comparing the earlier register kernel with public implementations. The persistent CUDA port has since been evaluated at 2.382249×; see the [current experiment record](../../EXPERIMENTS.md) for verified results. Leaderboard snapshots and proposed next steps below describe the time of this investigation.


The strongest public starting point found is **alygg77’s recorded 2.4015× implementation**, derived from vjeux’s native CUDA MoE kernel. It replaces our execution decomposition rather than adding another prefetch mechanism to our existing Gluon GEMMs. Its distinguishing features are full-K skinny work units, activation reuse in registers, a persistent grid spanning the complete operator, cost-balanced Stream-K scheduling, and a separate RS-WGMMA path for larger batches. We have not reproduced that score. The latest authenticated leaderboard snapshot showed **dolanzhao at 2.7578×**, but this search found no attributable public implementation or writeup explaining that entry. We should adopt the licensed, inspectable architecture as a control, preserve conservative BF16 semantics in a separate port, and measure the remaining gap instead of attributing guessed techniques to the leader. ([Published results](https://github.com/alygg77/okc-muse-spark-kernels/blob/6cae49a639ee6d14b929a5fd4a63c627f96d7dc0/results.json), [official board](https://openkernelchallenge.dev/leaderboard?problem=muse_moe_w4a16))

The public evidence is unusually reproducible. At commit `6cae49a639ee6d14b929a5fd4a63c627f96d7dc0`, the MoE Python file’s SHA-256 is `b33070898927b7b92df6c7a2515f9c02dd12723c43ca63682fa164e915dd4281`, matching the published record for judge job `e1bcad5a55cd4a29`: **2.4015×, interval 2.3655–2.4376**. The repository attributes most performance to vjeux commit `f35a41ee1c13e316dabbf772830d47b23b453393`; alygg77’s KPERM3 improvement contributes approximately **1.25%**, not the entire result. Both projects use Apache-2.0, so a port must retain their attribution and notices. ([Results](https://github.com/alygg77/okc-muse-spark-kernels/blob/6cae49a639ee6d14b929a5fd4a63c627f96d7dc0/results.json), [NOTICE](https://github.com/alygg77/okc-muse-spark-kernels/blob/6cae49a639ee6d14b929a5fd4a63c627f96d7dc0/NOTICE))

| Mechanism | Our current implementation | Public CUDA architecture |
|---|---|---|
| Skinny work unit | 64 output rows, repeated 256-K steps | 16 output rows × full K; eight warps divide K |
| Activations | Gathered and exchanged through shared memory each K step | Register slices retained across output-row units |
| Scheduling | Separate projection launches and work plans | Persistent whole-operator grid with skinny/fat jobs |
| Large batches | BF16 `mma_v2` projection kernels | Four RS-WGMMA consumer warpgroups and two producer warps |
| Partial work | Fixed split factors in our experiments | Cost-weighted K-stage ranges; boundary-unit fixups |

For the skinny path, each warp handles a disjoint 512-K slice of a 16-row full-K unit. Codes and original scales occupy **36 KiB**, transferred into a compressed shared-memory ring. Activations are loaded when the job changes and reused across output units. Cross-warp partials combine at the unit boundary. Our original tile instead performs two activation-exchange barriers per 256-K step—32 across K4096. Our unsuccessful weight-producer experiments retained that basic decomposition, so they did not test the public architecture. ([Pinned source](https://github.com/alygg77/okc-muse-spark-kernels/blob/6cae49a639ee6d14b929a5fd4a63c627f96d7dc0/kernels/muse_moe_w4a16.py))

For larger batches, the public engine keeps decoded weights in registers for RS-WGMMA, rather than sending expanded BF16 weights through shared memory. It partitions work using token-count-dependent costs, overlaps phases, and applies Stream-K fixups at range boundaries. This differs from uniformly splitting every output tile and writing all partials to global buffers. Published latency gaps versus ours are largest at M1 and M128/256, making a broad operator replacement more credible than optimizing routing alone. These measurements come from different runs and inputs, not a controlled comparison. ([Public timings](https://github.com/alygg77/okc-muse-spark-kernels/blob/6cae49a639ee6d14b929a5fd4a63c627f96d7dc0/RESULTS.md), [our scored profile](../../profiles/register_ready.9cf7ef93107b4052.txt), [Stream-K paper](https://arxiv.org/abs/2301.03598))

Adoption requires two explicit audits. Prepared weights appear lossless: packed FP4 codewords, original scale bytes and global scales, byte-permuted layouts, and a small scale-decoding lookup table; inspection found no persistent expanded BF16/FP32 weight matrix. However, public epilogues retain gate/up/SiLU and norm-weighted values in FP32 where our implementation rounds at BF16 boundaries. This is higher internal precision, not evidence of a lower-precision shortcut, but it is not strict staged-BF16 reproduction. A conservative port must insert both gate/up and SiLU roundings, plus BF16 rounding before and after norm weighting, across skinny, fat and WGMMA paths. Its performance cannot inherit the public score. ([Source](https://github.com/alygg77/okc-muse-spark-kernels/blob/6cae49a639ee6d14b929a5fd4a63c627f96d7dc0/kernels/muse_moe_w4a16.py), [challenge specification](https://openkernelchallenge.dev/problems/muse_moe_w4a16))

Cold compilation is the other risk: authors report approximately **273–275 seconds**, one **311.9-second** failure against the 300-second budget, and a lean build at 208–224 seconds. Preserve all four shape-dispatch variants and the selected alternate `helper0` CUDA source. A justified build experiment is to eliminate unreachable BIG=true instantiations only inside TINY/TINY2/MID builds, removing their attribute-setting and both launch references; MAIN still requires both versions. This preserves reachable mathematics but remains unmeasured. ([Measured facts](https://github.com/alygg77/okc-muse-spark-kernels/blob/6cae49a639ee6d14b929a5fd4a63c627f96d7dc0/docs/H200_MEASURED_FACTS.md), [module source](https://github.com/alygg77/okc-muse-spark-kernels/blob/6cae49a639ee6d14b929a5fd4a63c627f96d7dc0/kernels/muse_moe_w4a16.py))

The implementation sequence should therefore preserve an exact attributed control, prepare a separately named conservative BF16 port, and reproduce compilation, correctness and fresh-input replay behavior before tuning. After reproduction, the strongest evidence-backed performance target is unit-end release, fixup and phase-transition overhead. The authors already report streaming near their size-matched bandwidth ceiling and negative results from deeper rings. Reaching 2.7× from 2.4015× requires roughly another **11% latency reduction**; that is a target, not an established trick. Our current exhausted GPU-check quota prevents validation now, and the seven authorized scored submissions are already spent. ([Measured facts](https://github.com/alygg77/okc-muse-spark-kernels/blob/6cae49a639ee6d14b929a5fd4a63c627f96d7dc0/docs/H200_MEASURED_FACTS.md), [negative results](https://github.com/alygg77/okc-muse-spark-kernels/blob/6cae49a639ee6d14b929a5fd4a63c627f96d7dc0/docs/NEGATIVE_RESULTS.md))
